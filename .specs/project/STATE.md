### AD-002: Not a forecast — deterministic transaction generation (2026-07-05, supersedes the projection framing)

**Decision:** Instead of a statistical forecast, the feature generates concrete future `FinancialTransaction` rows from a bounded recurrence/installment definition. The existing dashboard shows the look-ahead for free. No averages, no projection math — "just use what's registered." v1 requires a start AND end (no infinite recurrence). Occurrences share a `seriesId`. Feature renamed spending-forecast → recurring-transactions.
**Reason:** User reframed at the spec checkpoint: they want to register "expense X, 12 parcels" and have 12 real transactions generated, not a computed projection. Simpler, explainable, and dashboard-compatible.
**Trade-off:** Variable/one-off spending is not anticipated at all (only registered commitments appear); bulk rows instead of a lightweight computed view.
**Impact:** Reuses existing `frequency`/`parcelsNumber`/`startDate`/`endDate`; adds a `seriesId` column (via `ddl-auto=update`). No dashboard changes needed.

### AD-003: In-progress installments via a "current parcel" input (2026-07-11)

**Decision:** Refine RECUR-10 so an installment can be registered mid-way. Input = total `N` + **current parcel `k`** (default 1); the generator produces parcels `k..N` **inclusive** (`N − k + 1` rows), the `startDate` is the month of parcel `k`, and descriptions carry the real `k/N..N/N` numbers. `k = 1` reproduces the original `1/N`-from-start behaviour exactly (backward compatible). The implied end is shown **read-only** in the form (no separate end-date input — that would duplicate `N` and re-open the count-vs-end conflict). Installments only; recurring is untouched.
**Reason:** The original generator always assumed the first parcel, so a purchase the user is already several parcels into either got wrong labels or double-counted parcels already imported from the Nubank CSV. User chose the "current parcel" framing (over "next" / "already paid") at the refinement checkpoint.
**Trade-off:** No automatic dedup against CSV imports — avoiding double-counting relies on the user setting `k` to the first not-yet-imported parcel. New `currentParcel` field threaded through DTO → generator → form.
**Impact:** Adds `currentParcel` to the series request DTO (backend + frontend), changes `generateInstallments` to a `k..N` loop with cap on the generated count, adds a service `1 ≤ k ≤ N` guard, and a form current-parcel input + read-only computed end. No schema change (no new column). Tasks T13–T17.

### AD-004: Shared Plans model replaces the "household" framing (2026-07-11)

**Decision:** Design the M4 Share milestone as **Shared Plans** — a spreadsheet-style shareable container — instead of the original "household / merge two users into one scope" framing. A `Plan` owns transactions and categories; a user belongs to many plans via `PlanMembership` with a role (OWNER | EDITOR | CONTRIBUTOR | VIEWER). Access is **two-layer**: plan role × row-level ownership (`created_by`) — a Contributor edits only their own rows, everyone sees everything, only the Owner manages members/categories/plan. Categories are shared at the plan level with a plan-total spending limit; the dashboard is combined + per-person. Every user gets an auto-created personal plan and their existing data migrates into it. Invites work by email and by link. Specced in `.specs/features/shared-plans/` (spec.md + context.md); ROADMAP M4 updated.
**Reason:** At the sharing-model checkpoint the user described "sharing like an Excel spreadsheet" with finer-grained access (a person adds/edits their own things but not the rest). The household model can't express privacy, read-only, or partial sharing; the container model subsumes it (a two-person shared plan _is_ a household) and adds those.
**Trade-off:** More entities (Plan, PlanMembership, PlanInvitation) and a more involved authorization layer than a single household flag. The auto-created default plan is a normal, **shareable** plan (user decided 2026-07-11 — no private/immutable "personal" space); only guard is a user can't delete/leave their last plan.

### AD-005: Shared Plans — active-plan transport via path variable `/plans/{planId}/...` (2026-07-12)

**Decision:** Plan-scoped requests carry the active plan as a URL **path variable** (`/plans/{planId}/financial-transaction`, `.../financial-transaction-category`, `.../dashboard`), resolved server-side into a `PlanContext(plan, user, role)` by a `PlanContextArgumentResolver` that reads the URI template var and verifies membership. Plan-**management** endpoints (create/list plans, invitations) stay user-scoped and are not nested. The plan is deliberately kept **out of the JWT** (email-only subject unchanged) so switching plans needs no re-login.
**Reason:** User chose the path approach over an `X-Plan-Id` header after a trade-off discussion, prioritizing "do it the standard/explicit way" while learning. Path scoping is structural — it can't be silently forgotten (no cross-plan leak) — and follows mainstream resource-hierarchy REST (GitHub-style). Header was the lower-churn alt but relies on discipline and hides the context.
**Trade-off:** Rewrites the existing flat transaction/category/dashboard routes under a `/plans/{planId}` prefix (cheap now, small codebase). Frontend service hooks build URLs under `/plans/${activePlanId}/...` and include `activePlanId` in TanStack Query keys (switch = natural refetch).
**Impact:** `ApiRoutes` gains a plan prefix for scoped routes; controllers swap `User loggedUser`-scoping for a `PlanContext` param (`@AuthenticationPrincipal` still identifies the actor for row-ownership/attribution). Recorded in `design.md` (Tech Decisions). Design phase essentially complete; next is Tasks.

### AD-006: Plan deletion is a soft delete (2026-07-12)

**Decision:** PLAN-10's "delete plan" is a **soft delete** — add a nullable `plans.deleted_at` (Flyway `V4`) and `Plan.deletedAt`; deleting sets the timestamp and archives the plan for all members. Dependent rows (transactions, categories, memberships, invitations) are **never cascaded/destroyed**. Archived plans are filtered out at the read paths (list-my-plans, `PlanContextArgumentResolver`, login-default, and the last-plan guard) via **explicit per-finder `deleted_at IS NULL`** conditions — deliberately NOT a global Hibernate `@SQLRestriction`, which would break `membership.getPlan()` association loads for a soft-deleted plan. Atomized as T42 (foundation) + T43 (rename+soft-delete) in tasks.md.
**Reason:** User flagged a hard cascade delete as too risky/unprofessional. Soft delete makes deletion reversible, keeps an audit/history trail, and defers the truly destructive operation.
**Trade-off:** A schema column + a handful of filtered finders (vs. zero-churn hard delete). Archived rows accumulate until a future purge exists.
**Impact:** Replaces the earlier "service-level cascade vs `ON DELETE CASCADE`" open question (now moot). Permanent deletion + retention is deferred (see Deferred Ideas).

### AD-007: Expense Items — item-level category attribution via a partition invariant (2026-07-15)

**Decision:** Line items are an **additive** child of `FinancialTransaction` (`TransactionItem`, mirroring `TransactionParticipant` — `@OneToMany` cascade+orphanRemoval, migration V7, no backfill). Each item carries its **own** category + amount. The dashboard **category breakdown** becomes item-aware via a **Partition Invariant**: a transaction's `amount` is sliced across category buckets exactly once — categorized items → their own category; uncategorized items + the un-itemized remainder → the parent transaction's category. Sums are **loose** (`0 ≤ Σitems ≤ amount`; overflow rejected), so the remainder bucket is always ≥ 0. Computed as `spent[C] = A[C] − B[C] + I[C]` (A = `SUM(ft.amount)` by parent cat = today's query; B = categorized-item sums by parent cat; I = categorized-item sums by item cat), extracted into a **pure `CategoryBreakdownAssembler` with unit tests**. Items and participants are **independent axes** (items = *what*, participants = *who owes*); **no new authz gate** (reuse transaction modify/create guards); update is **full-replace** (no business key). Applies to **both** CREDIT and DEBIT. **No "Uncategorized" bucket** in v1 — a category-less transaction's remainder stays out of the breakdown (as today), but a categorized item on it still surfaces.
**Reason:** The driving need is "cleaning vs. food inside one grocery run" — answerable only if the item is the unit of category truth. Loose sums avoid forcing the user to itemize taxes/freight; the remainder has a defined home on the parent category. The `A−B+I` decomposition turns the only hard query into three plain aggregations.
**Trade-off:** Rewrites the one category-keyed dashboard query (`buildCategoryBreakdown`) and touches PLAN-07 limit evaluation downstream; more entities than a flat "notes" field. **Top-line totals (income/expense/net) provably never move** — they don't read categories.
**Impact:** Specced/designed/tasked in `.specs/features/expense-items/` (ITEM-01..14, 14 tasks). No code yet. First execution pass = P1 (T1–T10); P2/P3 deferred.

**Resolution:** The vestigial `frequency` column and all backend/frontend references were removed in Recurrence Model v2 T1 (backend commit `78d9959`, migration `V9__drop_frequency_column.sql`). ### B-002: Login with an unrecognized email returned 500, not 401 (found 2026-07-17) — ✅ FIXED 2026-07-19 (`b23d940`)

**Discovered:** 2026-07-17, by `AuthenticationIT.loginForUnknownEmailIsRejected` during test-foundation T12.
**Impact:** `POST /auth/login` with an email that has no matching user threw `InternalAuthenticationServiceException` wrapping `UsernameNotFoundException` inside Spring Security's auth manager. `GlobalExceptionHandler` maps `BadCredentialsException` (wrong password) to 401 but had no handler for this wrapped exception, so it fell through to the generic handler → HTTP 500. A wrong password correctly returned 401; an unknown email incorrectly returned 500 — inconsistent, and (the real risk) the differing response let a caller **enumerate registered emails**.
**Resolution:** Fixed 2026-07-19 (`b23d940`). Root cause: `CustomUserDetailsService` threw a *custom* `UserExceptions.UsernameNotFoundException`, which `DaoAuthenticationProvider` did not recognize as a user-not-found (so it wasn't hidden/converted). Changed it to throw Spring Security's own `UsernameNotFoundException`; `hideUserNotFoundExceptions` (on by default) now converts it to `BadCredentialsException` → the existing 401 handler with generic "Invalid username or password." body. Unknown-email and wrong-password are now byte-identical in status AND body (new `AuthenticationIT.unknownEmailAndWrongPasswordAreIndistinguishable` test proves it). Removed the now-dead custom exception + its 404 handler mapping. `./mvnw clean verify` green (55 unit + 59 integration).

### B-003: Negative top-level transaction amount was accepted, not rejected (found 2026-07-17) — ✅ FIXED 2026-07-19 (`c62e7be8`)

**Discovered:** 2026-07-17, by `TransactionCrudIT` during test-foundation T13.
**Impact:** `FinancialTransactionRequestDto.amount` carried only `@NotNull` (no `@Positive`); a PUT/POST with `amount: -50.00` and no line items succeeded (200) and persisted the negative value, silently skewing dashboard totals. Item-level amounts were already guarded.
**Resolution:** Fixed 2026-07-19 as part of the consistency-review commit `c62e7be8`: added `@Positive(message = "Amount must be positive.")` to `FinancialTransactionRequestDto.amount`, mirroring the item-level guard. The IT was updated to assert rejection (`putWithNegativeTransactionAmountIsRejected`). Suite green.

### L-002: Frontend build-green ≠ runtime-correct for Base UI context (2026-07-12)

**Context:** During Shared Plans UAT, the plan switcher threw `Base UI: MenuGroupRootContext is missing` at runtime, though `npm run build` (tsc + vite) had passed clean.
**Problem:** Base UI compound components (e.g. `Menu.GroupLabel` needing a `Menu.Group` ancestor) enforce their parent-context requirement at RUNTIME, not in the type system — so a missing wrapper compiles fine and only fails on render/interaction.
**Solution:** Wrapped `DropdownMenuLabel` + the radio group in `DropdownMenuGroup` (the pattern the component's own `.stories.tsx` uses). Fixed in `07b5e92`.

### L-004: Re-verify migration numbering against reality at the start of Execute, not just at planning time (2026-07-13)

**Context:** Expense Splitting's design.md/tasks.md (written 2026-07-12) assumed the feature's migration would be `V5__add_transaction_participants.sql`. By the time a fresh session executed T1, an unrelated `V5__translate_default_plan_names.sql` had already landed on `main` (a same-day i18n fix), so V5 was taken.
**Problem:** Planning artifacts capture repo state as of the planning session; if Execute runs in a later session (by design — "planner doesn't execute", see [[execution-in-separate-chat]]), the repo may have moved on in the interim.
**Solution:** Before T1, checked `ls db/migration/` against the plan's assumed filename, found the collision, renumbered to V6, and recorded a `SPEC_DEVIATION` note at the top of tasks.md rather than silently adjusting.
**Prevents:** Assuming a spec/design/tasks artifact's file-numbering, line numbers, or "next available X" claims are still accurate — always re-check against the current repo state as the first step of Execute, and log any drift explicitly.

### L-003: Local Postgres isn't always the DB — check for a tunnel before declaring "DB unavailable" (2026-07-12)

**Context:** Starting Part 2 execution, `pg_isready`/`systemctl` showed local Postgres inactive and unstartable without a sudo password.
**Problem:** Assumed the DB was simply down and planned to defer DB-dependent tasks (schema migration boot-verify, runtime E2E).
**Solution:** The user reconnected an SSH tunnel (port-forwarded `localhost:5432` to the real dev/remote instance via an active `ssh` process) — `ss -tlnp | grep 5432` showed the tunnel, and `pg_isready` then succeeded. No local Postgres service is actually used in this workflow.
**Prevents:** Before concluding "the database is unreachable," check `ss -tlnp | grep 5432` for an existing SSH-tunneled listener, not just `systemctl status postgresql` — the two are unrelated and only the tunnel matters here.

### L-005: The SSH tunnel's local listener staying up does NOT mean the connection is alive — always probe with a timeout (2026-07-15)

**Context:** During Expense Items T14 E2E, `ss -tlnp | grep 5432` showed the tunnel's local listener present and the `ssh` process alive throughout, but `psql`/Spring Boot boot attempts hung or failed with "connection has been closed" — twice in the same session, including right after the user reconnected the tunnel.
**Problem:** `ss`/`ps` only prove the local end is listening and the process hasn't exited; they say nothing about whether the remote transport is actually alive. A plain `psql ... -c "SELECT 1"` with no timeout can hang indefinitely on a half-dead tunnel, wasting time before the problem is even noticed.
**Solution:** Always wrap connectivity probes in `timeout N` (10-15s) and treat exit code 124 as "tunnel is stale," distinct from a clean connection-refused. When it recurs after a user-reported reconnect, don't keep silently retrying — surface it and ask whether to keep waiting or hand off, rather than burning turns on an infrastructure problem outside the agent's control.
**Prevents:** Trusting `ss -tlnp`/process-alive checks as proof of DB reachability; burning time on unbounded `psql` calls against a flaky tunnel instead of a quick timeout-guarded probe.

### L-006: A dev server on a non-default port needs its port added to the backend's `ALLOWED_ORIGINS`, or CORS silently fails as "An error occurred" (2026-07-15)

**Context:** For Expense Items T14's FE visual pass, Vite was started on `:5183` (to avoid the user's own dev server already running on `:5173`) pointed at a throwaway backend on `:3099`. Registration failed in the browser with a generic toast ("An error occurred") and no other symptom.
**Problem:** `SecurityConfig.corsConfigurationSource()` reads `ALLOWED_ORIGINS` as a literal comma-separated allow-list (`.env` ships only `http://localhost:5173`); a request from any other origin is silently blocked by CORS, and the frontend surfaces this as a generic network-error toast, not a CORS-specific message.
**Prevents:** When running a throwaway frontend instance on a non-default port against a throwaway backend instance, export `ALLOWED_ORIGINS` for that backend instance to include the exact `http://localhost:<port>` used — don't assume the default `.env` value covers it. A generic "An error occurred" toast on register/login in a throwaway E2E setup is a CORS-origin-mismatch smell before anything else.

### L-007: A migration file on disk can get auto-applied to the real DB before it's even committed, if another process boots against the same database (2026-07-16)

**Context:** During series-edit's T12 pre-flight, `dev_finsight`'s `flyway_schema_history` showed V8 already `installed_on` 2026-07-16 21:47:09 — a minute before this session committed the V8 migration file (21:48:30).
**Problem:** Spring Boot runs Flyway automatically on every application boot. The migration file existed on disk (written by an Execute sub-agent) before it was committed; the user's own separately-running dev backend instance auto-reloaded/restarted in that window and picked it up, applying it straight to the real DB — bypassing the planned copy-DB verification gate entirely. No agent command caused this.
**Solution:** Verified safety via read-only checks against the real DB directly (definition-per-series 1:1 count, zero unlinked FKs, zero SPLIT-01 invariant violations, spot-checked backfill correctness) — these checks are strictly stronger evidence than a copy-DB check would have been, since they're against the actual production-adjacent data. Informed the user immediately rather than silently proceeding; they confirmed treating this as satisfying the integrity gate.
**Prevents:** Assuming a migration file is inert until `git commit` or until *this session* boots the app — if a dev database is shared with another running instance (an IDE run config, a user's own `npm run dev`-equivalent backend, hot-reload), a migration file merely existing on disk is enough to trigger auto-apply the moment ANY app instance restarts against that DB. When starting a copy-DB verification pass, check `flyway_schema_history` on the REAL DB first (not just the copy) to catch this before assuming a clean "pre-migration" baseline exists.

### L-008 (OBSOLETE as of 2026-07-25 — Testcontainers removed; kept for history): This machine's Docker Desktop needs two non-default env vars before Testcontainers will boot (2026-07-17)

**Context:** Standing up test-foundation's T6 harness smoke IT, `./mvnw verify` failed through four distinct errors in sequence before Testcontainers actually worked: (1) `docker info` succeeded but Testcontainers said "Could not find a valid Docker environment" — the active Docker context (`desktop-linux`) uses socket `~/.docker/desktop/docker.sock`, not the `/var/run/docker.sock` Testcontainers checks by default; (2) even with `DOCKER_HOST` pointed at `docker.sock`, every strategy failed — Docker Engine 29's daemon requires API ≥1.44, but testcontainers 1.21.x's bundled docker-java always probes with a hardcoded API 1.32 first (upstream bug, fixed in testcontainers 2.x: https://github.com/testcontainers/testcontainers-java/issues/11210); (3) after pinning the API version, `docker.sock` itself turned out to be a path-translating proxy — starting the Ryuk cleanup container failed with "mounts denied: /socket_mnt/... is not shared from the host" because that host path isn't in Docker Desktop's file-sharing allowlist; (4) switching `DOCKER_HOST` to `docker.raw.sock` (talks directly to the VM's dockerd, no path translation) fixed the mount error, but Ryuk's own container then failed to start/was immediately not-found.
**Problem:** None of these are code defects — they're this specific Docker Desktop-on-Linux installation's socket topology and a real upstream version-negotiation bug. Without knowing the exact fix, each symptom looks like "Docker isn't set up," which would wrongly block the whole test-foundation feature.
**Solution:** Three things, together, make `mvn verify` boot the harness on this machine: (a) `backend/src/test/resources/docker-java.properties` with `api.version=1.44` (committed — this is a real fix for anyone on Docker Engine 29+, not machine-specific); (b) `export DOCKER_HOST=unix:///home/lcs/.docker/desktop/docker.raw.sock` (machine-specific, NOT committed); (c) `export TESTCONTAINERS_RYUK_DISABLED=true` (machine-specific — Ryuk's container never starts cleanly here, but a plain JVM shutdown hook still removes the Postgres container on normal exit, confirmed via `docker ps -a` after a run). All three must be set together for `./mvnw verify` to reach the Testcontainers-backed `*IT` tests.
**Prevents:** Re-diagnosing this from scratch in a future session. If `./mvnw verify` fails with "Could not find a valid Docker environment," "client version ... too old," or "mounts denied," export `DOCKER_HOST` and `TESTCONTAINERS_RYUK_DISABLED` as above before assuming Docker itself is broken. Documented for future sessions/users in `TESTING.md` (T21).
