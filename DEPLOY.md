# Deploy checklist — findraco rebrand

The app has been renamed to **findraco**. Deploying the rebrand requires a few manual
Portainer/VPS steps in addition to the normal `git push` → GitHub Actions redeploy flow.

## Pre-deploy

- [ ] Confirm the Portainer stack env var has been renamed to `VITE_FINDRACO_API_URL`. The
  production nginx-served build falls back to same-origin `/api/findraco`, but any explicit value
  must use the new name.
- [ ] Confirm the API is no longer expected to serve the previous `/api` prefix. Old cached
  frontend bundles that call the old prefix will be forwarded by nginx and 404 at the API — this
  is expected and acceptable only during a full stack redeploy.

## Manual VPS steps

- [ ] Before deploying the time slice (V14, instants to `timestamptz`): confirm the API container
  runs in UTC with `docker exec findraco-api date`. The migration reads the old `timestamp` values
  as UTC; a container in another zone would shift every stored session, reset token and invitation
  expiry by that offset. If the zone is not UTC, stop and change the migration's `AT TIME ZONE`.
- [ ] Rename the Portainer stack to `findraco`. The GitHub Actions workflow only triggers a
  redeploy of the existing stack ID; the stack name itself is managed in Portainer.
- [ ] Update the Portainer stack comment/URL reference (the workflow error message mentions
  `/stacks/findraco?id=<STACK_ID>`).

- [ ] Before deploying the network slice (API reachable only through the proxy): set `SERVER_ADDRESS`
  in the Portainer stack env to the **docker0 gateway**, usually `172.17.0.1` (check with
  `ip -4 addr show docker0`). The compose file refuses to start without it, on purpose: an unset value
  must never bind the API on the public IP. The nginx container reaches the API through
  `host.docker.internal`, which is that same address.
- [ ] After that deploy, from outside the VPS: `curl http://<public-ip>:3000/api/findraco/v3/api-docs`
  must be refused (connection refused or timeout), and the site (`http://<public-ip>:<WEB_PORT>`) must
  still log in and load data. Swagger is no longer on the public IP; for a look at it, use an SSH tunnel
  (`ssh -L 3000:172.17.0.1:3000 <vps>`).
- [ ] Before deploying the authentication slice (decoded JWT key): the API now Base64-**decodes**
  `JWT_SECRET_KEY` and refuses to start when the result is under 32 bytes. Check the production value:
  `printf '%s' "$JWT_SECRET_KEY" | base64 -d | wc -c` must print 32 or more and not fail. If not,
  generate one with `openssl rand -base64 48` and set it in the Portainer stack env. Either way the
  access tokens issued before the deploy stop working once (they last 15 minutes) and the browser
  renews them from its session cookie without asking the user to sign in again.
- [ ] Before deploying the case-insensitive e-mail slice (V20, e-mails stored trimmed and lower-cased):
  run `backend/scripts/precheck-v20.sql` against production (see its header for the command). Both
  queries must return zero rows; a row is two accounts, or two pending invitations to the same plan,
  that would merge. Resolve them first, or V20 aborts and the deploy fails at start-up.

## Post-deploy

- [ ] Verify the browser tab shows the new favicon and the page title reads **findraco**.
- [ ] Verify the navbar, login, and register pages display the dragon-wing-and-coin logo.
- [ ] Toggle light/dark themes and confirm every page (login, dashboard, transactions,
  categories) renders legibly in both modes.
- [ ] Spot-check the 404 page (any unknown route) shows the themed centered logo + "Page not
  found" + home link.

## PWA

findraco installs as an app and works offline for its shell (the data still needs the network). The
worker, manifest, icons and `version.json` are generated by `pnpm build`; nginx serves them with the
cache headers below.

### How a release reaches installed apps

- [ ] A deploy replaces `sw.js` and `version.json` on the server. Installed apps look for a new worker
  at start-up, when they return to the foreground and every 60 minutes.
- [ ] The new worker installs in the background and waits. The app then shows the **New version
  available** toast with an **Update** button; closing the toast hides it for that version only.
- [ ] Until the member acts, the **Update to X** item in the account menu (and a dot on the avatar)
  stays. Tapping either activates the worker and reloads.
- [ ] A member who never taps gets the new version on the next cold start, once every window of the app
  is closed and opened again.

### Forcing an update (`minSupportedVersion`)

- [ ] `frontend/package.json` has `findraco.minSupportedVersion` next to `version`. Raise it in the
  release that must not run on older clients (for example a breaking API change). Apps older than it
  show a blocking **Update required** dialog whose only action is **Update**.
- [ ] Never set it above `version`: the build refuses (it would block the new version itself too). Equal
  to `version` forces everyone onto the release being built.
- [ ] The first PWA release commit must raise **both** `version` and `minSupportedVersion` to the
  release version. Until then `minSupportedVersion` holds the version before the PWA.
- [ ] The copy is neutral ("A new version of findraco is needed to continue.") and does not explain why.

### Emergency: a broken worker

If a worker misbehaves in production (stuck on an old shell, failing requests), replace `sw.js` on the
server with a worker that removes itself. Browsers fetch `sw.js` with `no-cache`, so every client picks
it up on its next check:

```js
self.addEventListener("install", () => self.skipWaiting());
self.addEventListener("activate", (event) => {
  event.waitUntil(
    (async () => {
      const keys = await caches.keys();
      await Promise.all(keys.map((key) => caches.delete(key)));
      await self.registration.unregister();
      const clients = await self.clients.matchAll({ type: "window" });
      clients.forEach((client) => client.navigate(client.url));
    })(),
  );
});
```

- [ ] To roll back, redeploy a build from a fixed commit: `pnpm build` writes a fresh `sw.js`, and the app
  registers it again on the next load. Do not leave the self-destroying file in place, or the app stays
  without a worker (it still works online, but loses offline start and the update flow).

### Good to know

- [ ] An app installed on iOS has its own cookie storage, separate from Safari: each member signs in
  once more inside the installed app.
- [ ] nginx headers (`frontend/nginx.conf`): `no-cache` for `index.html` (and the SPA fallback), `sw.js`,
  `version.json` and `manifest.webmanifest`; `public, max-age=31536000, immutable` for `/assets/`.
  `/api/` is never cached by the worker.

### UAT after the first PWA deploy

- [ ] Android (Chrome): install from the account menu or the browser; the app opens without browser bars.
- [ ] iPhone (Safari): **Install app** shows the two steps; after **Add to Home Screen** the app opens in
  standalone mode and the menu no longer offers **Install app**.
- [ ] Open the installed app offline after at least one online visit: the shell loads (the sign-in or the
  "can't reach the server" screen, not a browser error page).
- [ ] After the next deploy: the update toast appears; close it, then use **Update to X** in the account
  menu; the app reloads on the new version.
- [ ] On iPhone, the bottom bar sits above the home indicator and toasts clear it.
- [ ] The status bar matches the theme in light and in dark, including after toggling the theme.
